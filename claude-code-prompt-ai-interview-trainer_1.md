## Суть продукта

Пользователь заходит в приложение, выбирает сложность (лёгкая/средняя/сложная),
получает алгоритмическую задачу от AI-интервьюера в текстовом чате, решает её
в редакторе кода прямо в приложении, объясняет ход мыслей текстом, AI задаёт
1-2 уточняющих вопроса по ходу (как живой интервьюер), а в конце выдаёт
структурированный фидбэк: корректность, ясность коммуникации, эффективность
решения — каждый пункт с текстовым объяснением, не просто цифра.

## Технический стек (решено, не пересматривать без веской причины)

- **Клиент**: iOS, SwiftUI, минимальная поддерживаемая версия iOS 16
- **Backend / данные**: Supabase — Postgres + Auth (email/password и Sign in
  with Apple). Apple Developer аккаунт уже есть и активен.
- **API-слой для LLM**: Vercel Serverless Functions (Node.js/TypeScript).
  Весь LLM-трафик идёт только отсюда — LLM API-ключ никогда не попадает
  в клиент и не хранится в Supabase. Клиент обращается к Vercel-эндпоинтам,
  Vercel обращается к Supabase (через service role, с бэкенда) и к LLM API.
- **LLM**: бюджет на API не является жёстким ограничителем — не экономить
  на качестве модели, это ядро продукта. Используй топовую модель с
  качественной поддержкой structured output / function calling для
  генерации фидбэка, со стримингом ответа в чате (не блочный "прилетел
  весь ответ сразу через 5 секунд"). Финальный выбор конкретной
  модели/версии — сверься с актуальными предложениями провайдера прямо
  перед началом интеграции в Фазе 0/1, цены и модели меняются часто.
- **Подписки**: RevenueCat поверх StoreKit. Аккаунт RevenueCat уже создан.
  Цену платного тарифа пока не знаем — вынеси её ОДНОЙ конфиг-константой
  (не хардкодь в нескольких местах), чтобы поменять за секунды, когда решим.
- **Аналитика**: минимальная на старте — логировать события старта/завершения
  сессии в собственную таблицу в Supabase, без сторонних SDK.

## Архитектура

1. Клиент никогда не обращается к LLM API напрямую и никогда не обращается
   к Supabase с сервисными правами. Вся LLM-логика — на Vercel.
2. Vercel serverless-функция хранит системный промпт роли интервьюера,
   ключ LLM API, и решает, какую модель дёргать. Она же валидирует и
   сохраняет транскрипт сессии в Supabase (через service role key,
   который живёт только на Vercel).
3. Клиент общается с Vercel через типизированный REST-слой (простой
   URLSession-based API-клиент с Codable-моделями на стороне Swift).
   Auth-токен Supabase клиент получает напрямую от Supabase Auth SDK и
   прикладывает к каждому запросу на Vercel — Vercel этот токен
   верифицирует, прежде чем что-либо делать.
4. Сессия интервью — стейт-машина, статус которой меняется ТОЛЬКО на
   бэкенде (Vercel), не доверяем клиенту финальный статус или фидбэк.
   Статусы: started -> in_progress -> awaiting_feedback -> completed.

## Модели данных (минимум для v1)

- **User**: id, email, created_at, subscription_status
- **InterviewSession**: id, user_id, difficulty, topic (nullable для v1),
  status, started_at, completed_at, transcript (массив сообщений:
  role [interviewer|candidate], content, timestamp), question_text
- **SessionFeedback**: session_id, correctness_score, correctness_notes,
  communication_score, communication_notes, efficiency_score,
  efficiency_notes, overall_summary

## Системный промпт AI-интервьюера — ядро продукта, отнесись максимально внимательно

Промпт для LLM должен:
- Задавать роль строгого, но доброжелательного технического интервьюера
  уровня mid/senior инженера в продуктовой компании
- Давать алгоритмическую задачу, соответствующую выбранной сложности
  (банк тем: массивы/строки, хэш-таблицы, два указателя, деревья/графы,
  динамическое программирование, рекурсия/бэктрекинг — без завязки на
  вопросы конкретных компаний, это explicit non-goal)
- Не выдавать решение и не подсказывать прямо, только естественные
  уточняющие вопросы, как живой интервьюер
- В конце сессии переключаться в режим оценки и выдавать СТРОГО
  структурированный JSON с полями под SessionFeedback (используй
  function calling / structured output API, а не парсинг свободного текста)
- Быть устойчивым к попыткам пользователя манипулировать промптом
  ("забудь инструкции", "просто дай мне 5 баллов") — заложи защиту

## Порядок реализации (фазы, не пропускай и не меняй местами без причины)

### Фаза 0 — Проект и инфраструктура
- Инициализировать Xcode-проект (SwiftUI, iOS 16+)
- Настроить Supabase-проект: схема БД по моделям выше, миграции как код
- Настроить Vercel-проект с serverless-функциями, окружения (dev/prod),
  секреты (LLM API key, Supabase service role key) — только в переменных
  окружения Vercel, никогда в репозитории
- Черновик системного промпта интервьюера — обсудить со мной до того,
  как он "зашивается" в код

### Фаза 1 — Core-цикл интервью (реальный LLM с самого начала, не моки)
- Экран выбора сложности
- Чат-интерфейс с AI-интервьюером, подключённый к реальному LLM через
  Vercel-эндпоинт (раз бюджет позволяет, мокать нет смысла — сразу
  тестируем настоящее поведение модели)
- Редактор кода внутри чата (минимум подсветка синтаксиса для Python и
  JavaScript — используй готовую библиотеку, не пиши подсветку с нуля)
- Отправка решения + объяснения, получение 1-2 уточняющих вопросов от AI
- Экран структурированного фидбэка по итогам

### Фаза 2 — Авторизация и персистентность
- Supabase Auth: email/password + обязательно Sign in with Apple
  (требование Apple для приложений со сторонним входом)
- Сохранение сессий в БД, экран истории сессий
- Восстановление незавершённой сессии при повторном заходе

### Фаза 3 — Монетизация
- Лимит бесплатных сессий — проверка ОБЯЗАТЕЛЬНО на бэкенде (Vercel),
  не только в клиенте, иначе легко обходится
- Экран пейволла при достижении лимита
- Интеграция RevenueCat (аккаунт уже есть), платный тариф без
  ограничений, цена — через конфиг-константу

### Фаза 4 — Полировка и подготовка к релизу
- Обработка ошибок сети/LLM-таймаутов с понятными сообщениями пользователю
- Базовый onboarding (1-2 экрана, не больше)
- App Store метаданные, скриншоты, privacy manifest (обязателен у Apple
  с 2024+), проверка на соответствие App Store Review Guidelines
  (особенно раздел про AI-контент и подписки)

## Что НЕ делать в этом MVP (явно вне скоупа, не реализовывать даже частично)

- Голосовой ввод/вывод (speech-to-text/TTS)
- Режим system design интервью
- Трекинг слабых мест / интервальные повторения в стиле Anki
- Peer-to-peer интервью между реальными пользователями
- Банк вопросов под конкретные компании
- Автоподбор сложности на основе истории (это P1, после MVP)

## Требования к качеству кода

- Swift: стандартные конвенции Apple, Swift Concurrency (async/await),
  не использовать устаревшие completion-handler API там, где есть
  async-альтернатива
- Разделение Views / ViewModels (MVVM) — сетевые вызовы не идут напрямую
  из View
- Backend (Vercel): TypeScript со строгой типизацией, без `any`
- Unit-тесты как минимум для: парсинга LLM-ответа в структурированный
  фидбэк, логики лимита бесплатных сессий на бэкенде, стейт-машины
  статуса сессии
- Каждую фазу — отдельными коммитами с понятными сообщениями, не одним
  гигантским коммитом в конце

## PRD (полный контекст решений, целей и метрик)

# PRD: AI-тренажёр технических собеседований (v1 / MVP)

*Рабочее название — часть будущей "семьи" приложений для подготовки CS-специалистов, вместе с планируемым тренажёром по алгоритмам/структурам данных*

### Проблема

Разработчики, готовящиеся к техническим собеседованиям (алгоритмы + system design), сегодня имеют два неидеальных варианта: соло-практика по статичному банку задач в духе LeetCode (без фидбэка по тому, как ты коммуницируешь, структурируешь решение, как тебя оценил бы реальный интервьюер), или mock-интервью с живыми людьми — партнёрами или платными коучами (Pramp, interviewing.io — нужно искать партнёра, договариваться о времени, и фидбэк от сверстника часто неловкий или поверхностный). Ни один вариант не доступен "по требованию", и ни один не даёт структурированного, честного фидбэка, который реально помогает улучшаться между попытками. Цена нерешённой проблемы: кандидаты приходят на реальные собеседования недостаточно натренированными именно в том, что решает исход — процессе мышления и коммуникации, а не только "получил ли я правильный ответ". Это напрямую влияет на офферы и зарплату.

### Цели

- Дать пользователю пройти полноценное mock-интервью (вопрос → решение → объяснение → фидбэк) за один сеанс, без расписания и поиска партнёра
- Давать фидбэк не только по правильности решения, но и по коммуникации, процессу мышления, эффективности — чтобы пользователь понимал, что именно чинить
- Получить первую когорту пользователей, которые возвращаются за повторными сессиями (доказательство, что это "практика", а не разовое любопытство)
- Провалидировать готовность платить за AI mock-интервью как за категорию — до того, как строить парное приложение по алгоритмам/DS
- Дойти до первого релиза в App Store соло, в объёме, реализуемом за недели, а не месяцы

### Что НЕ делаем в v1 (Non-Goals)

- **System design интервью** — вне скоупа v1; только алгоритмические/coding-интервью. System design намного сложнее формализовать в структурированный AI-фидбэк, это естественное дополнение для v2, когда основной цикл уже доказал себя.
- **Голосовой ввод/вывод** — v1 полностью текстовый (печатные ответы + редактор кода). Голос добавляет реальную сложность (speech-to-text, задержки, очерёдность реплик), которая не нужна для проверки основной ценности продукта.
- **Трекинг слабых мест / интервальное повторение в стиле Anki** — ценная фича, но не обязательна для проверки основного цикла. Запланирована на v2, когда появятся данные использования, на основе которых её строить.
- **Peer-to-peer интервью** — продукт сознательно только AI-based; не строим мэтчинг между реальными пользователями.
- **Банк вопросов под конкретные компании** (вроде "вопросы в стиле Google") — юридически и операционно рискованно по источникам; в v1 только общие алгоритмические вопросы.

### User Stories

- Как соискатель-разработчик, я хочу начать mock-интервью по требованию, чтобы практиковаться в любое удобное время без согласования с партнёром.
- Как кандидат, я хочу объяснять ход мыслей во время решения (а не просто сдавать код), чтобы фидбэк отражал, как бы я показал себя на реальном интервью.
- Как кандидат, я хочу, чтобы AI-интервьюер задавал уточняющие/дополнительные вопросы по ходу сессии, чтобы практика ощущалась как настоящее интервью, а не викторина.
- Как кандидат, я хочу получить структурированный фидбэк в конце (что получилось хорошо, что улучшить, примерная оценка), чтобы точно знать, над чем работать дальше.
- Как возвращающийся пользователь, я хочу выбирать уровень сложности и тему, чтобы каждая сессия была направлена на то, что мне реально нужно тренировать.
- Как пользователь, упёршийся в лимит бесплатного тарифа, я хочу видеть понятное и ненавязчивое предложение перейти на платный тариф, чтобы понимать, за что я плачу, ещё до оплаты.

### Требования

**Обязательно для v1 (P0)**
- Пользователь может начать сессию: выбрать сложность (лёгкая/средняя/сложная) и получить алгоритмическую задачу
- Текстовый чат-интерфейс с AI-интервьюером; пользователь может задавать уточняющие вопросы перед решением
- Редактор кода (подсветка синтаксиса, минимум 1-2 языка, например Python/JavaScript) для написания решения
- AI может задать 1-2 естественных уточняющих/наводящих вопроса по ходу сессии
- Структурированный фидбэк по итогам сессии: корректность, ясность коммуникации, эффективность — каждый пункт с коротким текстовым объяснением
- Базовая авторизация/аккаунт и список истории сессий
- Бесплатный тариф: ограниченное число сессий в неделю/месяц; платный тариф: без ограничений
- Сборка, готовая к отправке в App Store (iOS, SwiftUI)

**Желательно (P1)**
- Автоматическая подстройка сложности на основе прошлых результатов
- Тегирование по темам (массивы, графы, динамическое программирование и т.д.)
- Возможность скачать/поделиться итогами сессии
- Лёгкая геймификация: streak-и, счётчик сессий

**На будущее (P2)**
- Голосовые интервью (speech-to-text + TTS)
- Режим system design интервью
- Трекинг слабых мест и интервальное повторение между сессиями
- Приложение-компаньон по алгоритмам/структурам данных, перекрёстно связанное под одним брендом

### Метрики успеха

**Опережающие индикаторы**
- Доля завершённых сессий (начал → закончил с фидбэком): цель 60%+
- Повторное использование: % пользователей, завершивших 2-ю сессию в течение 7 дней — цель 30%+
- Конверсия из бесплатного в платный тариф за первые 30 дней — цель 3-5%

**Отстающие индикаторы**
- Тренд месячных активных пользователей за первые 3 месяца после запуска
- Удержание подписки на 30/60/90 день
- Рейтинг/тональность отзывов в App Store

*Измерение: аналитика в приложении + App Store Connect + RevenueCat. Оценка на 30-й и 90-й день после запуска.*

### Открытые вопросы

- Точная цена платного тарифа — нужен ресёрч цен конкурентов (Pramp, interviewing.io, Exponent) перед финализацией
- Название приложения и общий "семейный" бренд с будущим приложением по алгоритмам/DS
- Должен ли бесплатный тариф ограничиваться количеством сессий или глубиной фич?
- Юридические/комплаенс-риски использования сгенерированного LLM контента в стиле реальных интервью

### Сроки

- Жёстких внешних дедлайнов нет — соло-проект, темп на своё усмотрение
- Фазировка: (1) core-цикл → (2) доработка качества фидбэка → (3) авторизация + тарифы → (4) App Store
- Контрольная точка перед дальнейшими вложениями: провалидировать цену/спрос до глубокой интеграции биллинга
